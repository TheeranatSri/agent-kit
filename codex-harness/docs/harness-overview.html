Codex Harness Workflow

Claude Opus เป็นผู้ประสานงาน (orchestrator) Codex (gpt-6.1-sol) เป็นคนลงมือทำงานใน sandbox และคนตรวจงาน (User) ตัดสินใจทุกรอบ harness จะไม่ commit เองและไม่ retry อัตโนมัติ ทุกรอบต้องหยุดรอคนตรวจ

User→ Main Claude session→ Harness operator (Opus)→ Codex worker
บทบาทและสิทธิ์ วงจรของหนึ่ง job ไฟล์และ handoff วงจรการเรียนรู้ Structured lines กรณีศึกษา เริ่ม job
1 · Roles and layers

สี่ชั้น สี่บทบาท ใครทำอะไรได้บ้าง

แต่ละชั้นคุยกับชั้นที่ติดกันเท่านั้น คำสั่งไหลลง รายงานสั้นๆ ไหลขึ้น main session ไม่อ่าน codex.log เอง (ไฟล์ใหญ่หลาย MB และกิน context) แต่ให้ operator อ่านแล้วสรุปไม่เกิน 20 บรรทัด (LESSONS L9)

การกระทำ User Main session Operator Codex
กำหนด scope ของ job (path ที่เขียนได้, ขนาดรอบ)ตัดสินถาม user ก่อน แล้วเขียน task.mdไม่ไม่
ตัดสิน feedback / accept / rejectตัดสินส่งต่อให้ operatorรันคำสั่งเมื่อได้รับคำตัดสินที่ส่งต่อมาเท่านั้นไม่
ตอบคำถาม needs_input ของ Codexตอบเองส่งคำถามให้ user แบบคำต่อคำ ห้ามตอบแทนห้ามตอบแทนถามได้ตอนจบรอบเท่านั้น
รัน harness CLIได้ (เช่น monitor)ใช้ statusหน้าที่หลักไม่
อ่าน codex.log—ไม่อ่าน (L9)ได้เขียนออกมา
เขียนไฟล์ในโปรเจกต์—task.md, check, session log, lessonsไฟล์ review ใน .harness/เฉพาะ --scope + HANDOFF.md
git commit—คนเดียวที่ commitห้ามห้าม
ดึงข้อมูล BigQueryอนุมัติ SQLdry run แล้วดึงแบบ read-only หลัง user อนุมัติห้ามรัน BQห้าม: ยื่น data_requests แทน
เขียน lessonsทบทวนอนุมัติและ commitร่าง entryร่างใน HANDOFF "Lessons (draft)" ห้ามแก้ไฟล์ lessons

เมื่อ Codex ต้องการข้อมูลที่ไม่มี: ช่อง data_requests

  1. Codex จบรอบด้วย status: needs_input และใส่ SQL แบบ read-only (SELECT / WITH หนึ่ง statement) ใน data_requests พร้อม purpose, tables, expected_rows
  2. Operator รัน harness data <job> ซึ่งตรวจ SQL แบบ static: SELECT/WITH เดียว = OK, มี INSERT / UPDATE / DELETE / MERGE / CREATE / DROP / ALTER / TRUNCATE หรือหลาย statement = REJECT, อย่างอื่นที่แปลก = FLAG
  3. Main session แสดง SQL ให้ user ดู พออนุมัติแล้วจึง dry run (ดู bytes) แล้วดึงแบบ read-only เป็น parquet/csv
  4. harness data <job> --done file.parquet --note "..." คัดลอกไฟล์ไปที่ jobs/<job>/data/ แล้วปลุก Codex ใน session เดิม (นับเป็นหนึ่งรอบ)
2 · Lifecycle of one job

วงจรของหนึ่ง job: จาก scope ถึง lesson

ทุกกล่องสีเหลืองอำพันคือจุดที่คนต้องตัดสินใจ ชื่อในตัว mono คือคำสั่งหรือ status จริงใน harness.py ถ้าส่ง feedback งานจะกลับไปที่ Codex ใน session เดิม (codex exec resume กับ session_id เดิม) Codex จึงจำงานรอบก่อนได้

ในหนึ่งรอบ harness ทำอะไร

  • เขียน rounds/<n>/prompt.md (รอบแรกเป็น HARNESS RULES + LESSONS block + task.md ส่วนรอบถัดไปเป็นข้อความ feedback)
  • รัน codex exec (รอบ 1) หรือ codex exec resume <session_id> พร้อม --output-schema แล้วเก็บ log ทั้งหมดไว้ใน codex.log
  • รัน bash check.sh จาก root ของโปรเจกต์ แล้วบันทึกลง check.txt และ check_command.json
  • ตั้ง status: ถ้า codex exit ≠ 0 หรือไม่มี result = error, worker ส่ง done = awaiting_review, นอกนั้นใช้ status ที่ worker ส่งมา แล้วเขียน review.md และแจ้งเตือนบน macOS

กติกาที่ Codex ได้รับทุก job

  • เขียนได้เฉพาะ path ใน --scope และ HANDOFF.md ห้าม commit / push ไม่มี network
  • สร้าง HANDOFF.md ก่อนเริ่มงานอื่น ส่วน ## Status ต้องเป็นบรรทัดเดียวที่เขียนทับทุกครั้ง
  • ถามกลางรอบไม่ได้ ให้บันทึกสมมติฐานแล้วจบรอบด้วย needs_input + questions
  • ข้อความสุดท้ายต้องเป็น JSON: status (done | needs_input | blocked | failed), summary, files, questions, next, data_requests

ทำไมต้องมี handoff

ถ้า model ตัวไหนหยุดกลางทาง เช่น token หมด process ตาย หรือ session ถูกปิด อีกตัวต้องรับงานต่อได้ทันทีจากไฟล์ โดยไม่ต้องเดาจากความจำ จึงมี handoff ทุกชั้น และแต่ละไฟล์ใช้หัวข้อเดียวกัน: Status (หนึ่งบรรทัดปัจจุบัน) / Done / Next / Decisions & open questions / How to verify

  • Main session: notebooks/knowledge/session-log-<date>.md
  • Operator: .harness/OPERATOR_HANDOFF.md
  • Codex: .harness/jobs/<job>/HANDOFF.md
  • Claude agent ที่รันเบื้องหลัง: ไฟล์ที่ระบุไว้ใน prompt

รับงานต่อจาก model อื่น

  1. อ่าน state.json (session id, round) และหัวข้อ Next ใน HANDOFF.md
  2. ถ้าจะทำต่อใน Codex ใช้ harness feedback <job> "…" (resume session เดิม)
  3. ถ้าจะให้ model อื่นทำ ส่ง task.md + HANDOFF.md + review.md ล่าสุด

monitor แสดงบรรทัด Status ของ HANDOFF พร้อมอายุไฟล์ (นาที) และเหตุการณ์ล่าสุดใน codex.log ถ้า HANDOFF ไม่ได้อัปเดตนานจะเห็นได้ทันที (L2)

4 · The learning loop

ความผิดพลาดทุกครั้งกลายเป็นกติกาของ job ถัดไป

ทุก job ต้องจบด้วย retrospective ไม่ว่าจะ accept หรือ reject บทเรียนเรื่อง workflow (Claude, Codex, harness, git) ไปที่ ~/tools/codex-harness/LESSONS.md ส่วนบทเรียนเรื่อง domain ของโปรเจกต์ไปที่ไฟล์ lessons ของโปรเจกต์ (เช่น notebooks/knowledge/lessons.md)

  1. Codex ร่างเมื่อมีอะไรผิดพลาดก็เขียนไว้ใต้ ## Lessons (draft) ใน HANDOFF.md โดยห้ามแก้ไฟล์ lessons เอง
  2. harness lessonsรวบรวมข้อเท็จจริงต่อรอบ (check fail, needs_input, error, data rounds) และร่างของ worker ไว้ใน retro.md
  3. Operator คัดกรองเขียนเป็น entry ที่ Cause ต้อง verify แล้ว เลือก keep / merge / drop และระบุหลักฐาน
  4. Orchestrator อนุมัติทบทวนแล้ว commit ถ้า lesson ไหนกลายเป็นกฎ ให้บังคับใช้ใน worker rules, check หรือ skill
  5. ฉีดเข้า promptรอบแรกของ job ถัดไปจะได้ LESSONS block: ชื่อ + บรรทัด Prevent ของทุก entry ที่เป็น [who: codex] หรือ [who: both]

รูปแบบ entry

## L<n>. <short title>   [who: claude | codex | both] [area: ...]
- Problem: what went wrong (observable symptom).
- Cause: why it happened (verified, not guessed).
- Fix: what was done.
- Prevent: the rule / check that stops it next time.
- Seen: date, job / commit.

ไฟล์ของโปรเจกต์ใช้ prefix P<n> ส่วนไฟล์ของ harness ใช้ L<n>

ตัวอย่างจริงจาก drift job

## L13. A round with no size limit ran 37 min
##      and produced 21 files   [who: both] [area: process]
- Problem: round 1 took 37 min, wrote 21 files
  (drift_examples.csv 13.8 MB / 54,656 rows,
  report.md 89 KB / 914 lines) for 3 requested
  deliverables, with no short summary.
- Cause: task.md set no limits on time, number of
  files or output size (verified: state.json,
  result.json, task.md).
- Fix: round 2 feedback set 25 min, no new files,
  CSV under 5,000 rows, a 40-line summary.
- Prevent: every task.md states max minutes, allowed
  files, max output size, "no extra analyses".
- Seen: 2026-10-08, cdt-drift-analysis.
5 · Structured lines

เขียนเหตุผลเป็นบรรทัดที่ตรวจสอบได้

ทุก model เขียนข้อสรุป ข้อเสนอ และการตรวจสอบเป็นบรรทัดเดียวตามรูปแบบที่กำหนด IO-log hook จะดึงบรรทัดเหล่านี้ออกไปเก็บโดยไม่ต้องเรียก LLM เพิ่ม คำว่า verified ใช้ได้เมื่อมีหลักฐานจริงเท่านั้น (path, คำสั่ง, test, ตัวเลข) ถ้าไม่มีหลักฐานต้องเขียนเป็น hypothesis ทุกตัวอย่างด้านล่างคัดมาตามต้นฉบับจาก drift job

Claim
ข้อสรุปหรือสาเหตุ พร้อมสถานะและหลักฐาน
Claim: review ledger has 3,631 rows, below 5,000; 3,101 source-change groups preserve all 38,012 source material/layer records | Status: verified | Evidence: drift_examples.csv; source_differences.csv; independent group/count assertions.
Claim (refuted)
สมมติฐานที่ test หักล้างแล้วยังเก็บไว้ และกลายเป็น lesson
Claim: all 14 longivity rows would newly enter cores | Status: hypothesis | Evidence: refuted by direct comparison; only 13 new rendered cores; barcode 4005292004855 has the already-mapped underscore form.
Check
การตรวจงานวิเคราะห์ข้อมูล แบ่งเป็นขั้น source / scope / transform / method / result
Check: transform | source ledger | Criterion: unique BU/category/layer/source/old/new and exact full-detail row reconciliation | Actual: 3,101 groups, sum 38,012, no duplicates | Evidence: independent pandas group/count assertions; review_drift | Pass: yes
Proposal
ทางเลือกที่ต้องให้ user ตัดสิน พร้อมข้อแนะนำ
Proposal: source-contract | Options: A) Switch to reconciled view after approval B) Retain current feed pending authority confirmation | Recommend: B | Rationale: snapshots do not establish freshness or authority.
Decision
บันทึกสิ่งที่ user เลือก (By: user)
Decision: sanity-policy | Choice: detect/report only; code detects, people decide, CDT owner fixes | By: user | Note: no new LLM step or corrected-value mapping.
Assumption
สิ่งที่ตัดสินใจไปโดยยังไม่ได้คำตอบจาก user พร้อมความเสี่ยงและเวลาที่ต้องกลับมาดู
Assumption: round-1 metrics.json and verification.json must remain unchanged | Rationale: round 2 allows scripts/report/CSVs only | Risk: their output hashes and drift-row count are stale for changed round-2 artifacts | Revisit: metadata updates authorized; current verification is in this handoff/report.
Done
งานที่เสร็จพร้อมวิธี verify และ commit
Done: round-2 feedback implemented in existing files only | Verified: final check.sh exit 0; Ruff check/format pass; independent CSV assertions | Commit: none (harness worker prohibition)
Question · Failure
drift job ไม่มีสองแบบนี้ (worker ไม่มีคำถาม questions: []) จึงแสดงเฉพาะรูปแบบ
Question: <id> | To: user | From: <actor> | ...
Failure: want ... | actual ... | evidence ... | cause ... | Status: hypothesis|verified

เริ่ม job ใหม่

ก่อนรัน new ต้องถาม user ก่อนว่าต้องการอะไร: path ที่ Codex เขียนได้, ไฟล์ส่งมอบ, ขีดจำกัด (นาที, จำนวนไฟล์, ขนาด output) แล้วจึงเขียน task.md และ check ที่ exit 0 เฉพาะเมื่องานถูกต้อง ค่า default คือ model gpt-6.1-sol, effort medium (ใช้ --effort high กับงานออกแบบที่ยาก) และสูงสุด 5 รอบ (env HARNESS_MODEL, HARNESS_EFFORT)

# once per project: .harness/ + "Lessons and multi-model work" section in CLAUDE.md / AGENTS.md
harness init

# create the job (scope comes from the user)
harness new <job> --task task.md \
  --check-cmd 'test -s out/report.md && git diff --quiet -- src configs' \
  --scope out/ [--effort high] [--max-rounds 5] [--lessons notebooks/knowledge/lessons.md]

# round 1 in the background; tag who ran it in commands.log
HARNESS_ACTOR=operator harness run <job> --bg
harness monitor            # live table + macOS notification when a job needs you
harness status             # one-off: status, round, minutes, check, HANDOFF Status + age, last log event

# review, then the user decides
harness review <job>
harness feedback <job> -f feedback_r2.md --bg   # next round, same Codex session
harness accept <job>                            # or: harness reject <job> "why"

# the worker asked for data (needs_input +ndata)
harness data <job>                              # list requests + static SQL check
harness data <job> --done pulled.parquet --note "rows / columns" --bg

# always, accepted or rejected
harness lessons <job>                           # -> jobs/<job>/retro.md

# read the last logged command
tail -1 .harness/commands.log | python3 -m json.tool

task.md ที่ดีต้องมี

  • เป้าหมาย, inputs (read-only), output paths และสิ่งที่ห้ามแตะ
  • นาทีสูงสุด, ไฟล์ที่อนุญาต, ขนาด output สูงสุด และระบุ "no extra analyses" (L13)
  • โปรเจกต์ uv: ระบุ UV_CACHE_DIR=<scope>/.uv-cache และ --offline --no-sync (L14)
  • lesson entries ที่เกี่ยวข้องกับงานนี้

หลัง accept

  • main session รัน test ของโปรเจกต์ แล้ว commit เอง (harness ไม่ commit)
  • รัน harness lessons แล้วให้ operator ร่าง entry และ orchestrator อนุมัติ
  • อัปเดต session log, OPERATOR_HANDOFF.md และ HANDOFF.md ให้ Status เป็นปัจจุบัน
